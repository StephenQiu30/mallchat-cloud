# IM 通知中心 PRD

## 1. 背景

后端 notification-service 已支持通知新增、分页、我的通知、标记已读、全部已读、未读数、批量删除和事务提交后实时推送。chat-service 也会直接发送好友申请、好友通过、会话更新和消息事件。

随着 QQ-like IM 能力增长，通知需要承接好友申请、群邀请/审核、动态点赞评论、系统公告、@我、文件消息提醒等事件，避免各业务各自定义一套提醒入口。

## 2. 产品目标

1. MVP 保持通知中心可查看、可已读、可未读计数。
2. P1 统一好友、群、动态互动、系统通知的类型和跳转参数。
3. P2 支持免打扰、通知聚合、运营通知策略和管理端治理。

```gherkin
Given 用户收到一条好友申请
When 系统创建通知
Then 用户应能在通知中心看到该申请
And 在线时应收到实时通知事件
```

## 3. 非目标

- 不把聊天消息本身全部复制成通知记录。
- 不在首版实现复杂推送厂商通道。
- 不用通知表替代好友申请、动态评论等业务事实表。

## 4. 核心用户故事

### 4.1 普通用户

作为用户，我希望所有需要处理的事件都集中在通知中心。

验收标准：
- 通知列表展示类型、标题、内容、时间、已读状态和跳转目标。
- 用户只能查看自己的通知，管理员例外。
- 未读数与标记已读接口准确。

### 4.2 业务服务

作为业务服务，我希望用统一接口创建通知并实时推送。

验收标准：
- 通知创建支持幂等 `bizId`。
- 事务提交后再推送实时事件。
- 相关业务 ID 必须显式传入，不能依赖正文解析。

### 4.3 运营管理员

作为管理员，我希望可以发布系统通知和全员广播。

验收标准：
- 管理员可向全员、角色或指定用户组发布通知。
- 管理操作需要日志记录。
- 广播通知需要限流和审计。

## 5. 数据与权限边界

- `notification` 是通知展示和已读事实来源。
- 好友申请、群申请、动态评论等业务实体仍由各自领域维护。
- 通知的 `relatedType/relatedId` 用于跳转和追踪，不替代业务状态。

## 6. 首版验收门禁

- 好友申请、好友通过、系统通知至少接入通知中心或明确不接入原因。
- 新增类型必须同步枚举、DTO、VO 和测试。
- 通知未读数、已读、批量删除需保持现有行为不回退。

## 7. 风险与边界

- 直接聊天消息和通知中心消息边界要清晰，否则会话未读和通知未读会重复。
- 动态点赞评论的通知需要等动态 feed 事实表落地后再完整接入。

## 8. 待确认问题

- 好友申请是否同时保留 chat-service 实时事件和 notification 记录？
- 群邀请是否进入通知中心还是群通知页？
- 是否需要免打扰设置？
