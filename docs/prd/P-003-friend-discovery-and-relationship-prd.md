# 好友发现与关系 PRD

## 1. 背景

后端已有好友申请、同意/忽略、好友列表、双向好友关系、移除好友和私聊房间初始化能力。`UserController` 也提供用户分页搜索，可作为添加好友前的用户发现基础。

但 QQ-like IM 不只需要“能加好友”，还需要搜索发现、申请状态可见、备注分组、删除/拉黑、隐私限制和共同好友等关系体验。当前代码没有看到备注、分组、黑名单、来源渠道、申请过期和推荐好友模型。

## 2. 产品目标

1. 首版形成“搜索用户 -> 发起申请 -> 对方处理 -> 好友列表 -> 私聊房间”的完整闭环。
2. P1 支持好友备注、分组、删除关系后的私聊权限收敛。
3. P2 支持拉黑、隐私校验、共同好友和好友推荐。

```gherkin
Given 用户 A 搜索到用户 B
When 用户 A 发送好友申请且用户 B 同意
Then 系统应建立双向好友关系
And 返回或创建稳定私聊房间
```

## 3. 非目标

- 不在首版实现复杂通讯录导入、手机号匹配和推荐算法。
- 不把好友关系与关注、粉丝、动态订阅混为一套关系。
- 不破坏现有 `user_friend` 和 `user_friend_apply` 的基础模型。

## 4. 核心用户故事

### 4.1 添加好友用户

作为用户，我希望可以通过昵称、账号或手机号搜索用户并发送好友申请。

验收标准：
- 搜索结果应脱敏展示头像、昵称、简介和是否已是好友。
- 重复申请、互相申请、已经是好友、添加自己均应有明确错误或幂等结果。
- 好友申请消息长度和敏感内容有基础校验。

### 4.2 处理申请用户

作为收到申请的用户，我希望可以查看申请列表并同意或忽略。

验收标准：
- 待处理申请只允许目标用户处理。
- 同意申请后创建双向好友关系与稳定私聊房间。
- 忽略申请不创建好友关系。

### 4.3 好友列表用户

作为聊天用户，我希望好友列表展示在线状态、备注、分组和最近关系状态。

验收标准：
- MVP 展示头像、昵称、在线状态。
- P1 增加好友备注、分组排序、关系状态。
- 删除好友后，应阻止继续发送私聊消息。

## 5. 数据与权限边界

- `user_friend` 是双向好友事实来源。
- `user_friend_apply` 是申请流程事实来源。
- 好友搜索复用用户服务，但只能返回脱敏信息。
- 私聊消息发送必须继续依赖 `isMutualFriend` 校验。

## 6. 首版验收门禁

- 好友申请、重复申请、同意、忽略、删除好友、私聊权限至少有单元测试或集成测试覆盖。
- 好友发现接口必须限制分页大小与脱敏字段。
- 好友关系变更必须能触发实时通知或会话更新。

## 7. 风险与边界

- 好友删除后是否保留历史私聊房间和会话，需要产品确认。
- 拉黑与删除不是同一功能，不能用删除关系替代拉黑。

## 8. 待确认问题

- 用户是否需要唯一 MallChat 号？
- 好友备注、分组和黑名单是否进入 P1？
- 申请被忽略后是否允许再次申请，冷却期多长？
