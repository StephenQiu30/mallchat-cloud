# 动态 Feed PRD

## 1. 背景

用户明确希望后端支持“动态”等类似 QQ 的社交能力。当前全仓搜索未发现 moment、feed、timeline、dynamic、space 等后端领域表、控制器或服务。通知模块已有 comment、like、follow 等通知类型，但缺少动态实体和互动链路。

因此动态 feed 应作为独立后端功能点设计，不应混入 chat message 或 notification 表。

## 2. 产品目标

1. MVP 支持发布文字/图片动态、好友可见时间线、删除自己的动态。
2. P1 支持点赞、评论、评论回复和互动通知。
3. P2 支持可见性范围、置顶、精选、内容审核和管理端治理。

```gherkin
Given 用户 A 和用户 B 是好友
When 用户 A 发布一条好友可见动态
Then 用户 B 的动态流应能看到该动态
And 用户 B 点赞或评论后，用户 A 应收到通知
```

## 3. 非目标

- 不把动态当作聊天室消息写入 `chat_message`。
- 不在首版实现复杂推荐流、广告流和陌生人广场。
- 不在首版实现空间装扮、访客记录和相册体系。

## 4. 核心用户故事

### 4.1 发布动态用户

作为用户，我希望可以发布文字和图片动态，表达近况。

验收标准：
- 动态正文长度有限制。
- 图片引用文件服务上传结果。
- 用户只能删除自己的动态，管理员治理另行设计。

### 4.2 浏览动态用户

作为好友，我希望在动态流看到好友最近发布的内容。

验收标准：
- MVP 仅展示好友可见动态。
- 动态列表支持分页和时间排序。
- 被删除、被屏蔽或无权限动态不能返回。

### 4.3 互动用户

作为好友，我希望可以点赞和评论动态。

验收标准：
- 点赞应幂等，再次点击可取消或保持明确状态。
- 评论需要内容校验和权限校验。
- 点赞/评论可以触发通知服务。

## 5. 数据与权限边界

- 需要新增动态主体表、动态媒体表、点赞表和评论表。
- 动态可见性首版可先基于好友关系，后续扩展为公开、私密、部分可见、不给谁看。
- 通知服务只负责互动提醒，不作为动态事实来源。

## 6. 首版验收门禁

- 新增 OpenSpec 明确定义动态实体、可见性和互动权限。
- 发布、列表、删除、点赞、评论至少覆盖核心单元或集成测试。
- 与好友关系解除后的动态可见性需要明确规则。

## 7. 风险与边界

- 动态 feed 和 IM 会话是不同产品域，不应共享会话未读。
- 可见性规则一旦上线很难迁移，首版需要保守。

## 8. 待确认问题

- 动态是否只给好友看，是否需要公开广场？
- 删除好友后，历史动态是否继续可见？
- 评论是否支持二级回复？
